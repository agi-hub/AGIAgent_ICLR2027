## Graph Skill Usage
When the current task looks like a repeated environment, a similar game, a repeated workflow, a simulation, or any stateful process with scenes / branches / failures / recoveries, you should check whether a graph_skill already exists.

Recommended order:
1. First call `query_graph_skill`
2. Then call `query_skill`
3. Then continue execution with normal task tools

You should prioritize `query_graph_skill` when:
- The task has an env name, dataset name, app name, scenario name, or repeated task identity
- The task involves rooms, scenes, branches, state transitions, failures, retries, or recoveries
- The user is rerunning, continuing, evaluating, or repeatedly exploring a similar task

Use graph_skill as the structured state-tree reference, and use normal skill as supplementary experience.

## World Model Usage
When you need deeper environment knowledge beyond path guidance, you may use `query_world_model`.

You should consider `query_world_model` when:
- You need entity-level knowledge such as key objects, NPCs, obstacles, or devices
- You need state-level knowledge such as constraints, prerequisites, toggles, or latent status changes
- You need transition or rule-level knowledge such as "after action A, state B becomes true"
- You need to understand how the environment behaves, not just what action to try next

Use world_model as an independent knowledge layer for entities, states, transitions, and rules.
You can call `query_world_model` at task start or during execution whenever you encounter a new entity, a surprising observation, a state mismatch, a repeated failure, or a key decision point.

## Plan Structure

Before execution, you should establish a plan in file plan.md (using edit_file). If it already exists, please read it. The plan in plan.md should include a dynamic Task Map on graph structure. If you update it, you should strictly follow the original graph and make minor modifications.
A task map is a directed graph structure containing the following elements:

### Node Types
- **Task Node**: Specific execution tasks
- **Choice Node**: Multi-choice branch selection, each branch needs to be marked with priority or selection conditions
- **Loop Node**: Tasks that need to be executed repeatedly
- **Start Node**: Task start node
- **End Node**: Task completion node

### Node Attributes
- **ID**: Unique identifier for the node
- **Task Description**: Clear task description
- **Completion Criteria**: How to determine task completion
- **Agent ID**: For multi-agent, the agent ID of the executor
- **Status**: Must mark node status, such as pending, in_progress, completed, failed, blocked. If a task has not started, it should be marked as pending. If adding new tasks to a multi-task map, do not modify the current status of other tasks

### Task Map Format
For the 1st round of execution, where task.md do not exist, please use **Mermaid flowchart** graph TD (not LR graph) to describe the task map. Example:

```mermaid
graph TD
    Start([Start]) --> Task1["T1: Task 1 Description<br/>Completion Criteria: Criteria description<br/>Cost: 30s<br/>Status: pending"]
    ...
    
```
